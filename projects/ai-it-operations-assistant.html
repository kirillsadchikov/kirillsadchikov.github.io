THE PROBLEM

IT support time going to things that don't need a human

Most IT access requests follow the same shape: someone needs access to a system, for a reason, approved by someone. In practice they show up as Teams messages, half-written emails, or a hallway ask — which means incomplete information, no real audit trail, and IT chasing people for details that should've been there from the start. On top of that, people sometimes ask for more access than they actually need, just in case.

I wanted to see what that process looks like once it's actually built: a chat interface that asks the right questions, a workflow that routes it for approval, and a record of what happened and why.

APPROACH

Not everything should be the AI's job

The part of this I'd actually defend in an interview is the split: Copilot Studio handles the parts where language varies — understanding the request, answering policy questions, deciding what's missing. Power Automate handles everything that needs to be the same every time: who approves what, what happens on approval or rejection, what gets logged. AI is good at the first kind of problem and bad at the second — it shouldn't be making decisions that need to be predictable and auditable, and it should never be the one deciding who gets access to what.

THE WORKFLOW

A request becomes a tracked SharePoint item, not a message in a thread

Every request lands in an IT Requests list in SharePoint — requester, system, business justification, priority, approver, status. That's the system of record the rest of the flow works off of.

The IT Requests list — each row is a request with its own status and approval history.

Creating an item triggers the approval flow: it sets the item to Pending Approval, sends the approver a request by email, and branches on the decision.

The approval flow — trigger, status update, approval step, then branch on the outcome.

The approver gets the full request context and decides right from Outlook.

Both branches close the loop — approved or rejected, the requester gets a clear answer and the record stays updated.

THE AI LAYER

Grounded in three policy documents, nothing invented

The assistant only answers from documents I gave it — an IT access policy, an incident escalation guide, and an internal AI usage policy. It has one tool wired up (creating an access request), and explicit instructions to never ask for passwords, MFA codes, or any other credential, and to say so plainly when it doesn't know something rather than guess.

The agent's setup: instructions, one tool, three knowledge sources it's grounded on.

Asked a specific policy question, it answers with the actual number from the document and cites it — not a plausible-sounding guess.

GUARDRAILS

It pushes back on bad requests instead of forwarding them

Asked to submit a request for Global Administrator "in case it's useful later," it doesn't just relay that to an approver — it explains why that violates least privilege and asks for an actual business justification before proceeding.

A real exchange — the request was deliberately vague and over-privileged to see how the agent would handle it.

WHAT DIDN'T WORK YET

The agent can't actually submit the request on its own

The assistant correctly recognizes when someone wants to create a request and extracts all six required fields cleanly from the conversation. Where it breaks: the call from the Copilot agent into the Power Automate flow comes back with an HTTP 403, and the flow's run history shows zero executions — meaning it's getting blocked at the authorization boundary between the agent and the workflow, before anything in SharePoint happens.

Fields extracted correctly; submission blocked.

Monitoring confirms it: no runs ever reached the flow.

My best guess is a licensing or runtime-permission gap between the agent and the Power Platform environment in this particular tenant, rather than anything wrong with the flow itself — the same flow runs fine when triggered directly from SharePoint. Next step would be checking runtime entitlements in a fully licensed tenant, and trying the classic Agent Flow connection as a fallback if that doesn't resolve it.

WHAT'S NEXT

If I kept building this

Fix the agent-to-workflow permission issue, then move the knowledge base off uploaded demo files and onto permission-aware SharePoint sources. Add a status lookup so people can check their own request instead of asking. Add retries, owner notifications, and logging so failures don't go unnoticed. Then pilot it with a small group and actually measure the thing — self-service rate, approval time, how often it escalates instead of answering.
