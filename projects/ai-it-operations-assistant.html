The problem

Employees ask the same IT questions over and over, and submit access requests through unstructured messages — chat, email, hallway asks. That creates incomplete requests, manual follow-up for IT, no visibility into status, and approval records that are hard to reconstruct later. And a general-purpose AI assistant left ungrounded will confidently invent internal policy it was never given.

  • Repetitive IT/process questions consume employee and IT time
  • Access requests are vague, incomplete, or sent through inconsistent channels
  • Approvals are hard to track when they happen through scattered messages
  • Employees may ask for broader permissions than they need
  • An ungrounded AI assistant may invent internal policy details

Design decision: where AI ends and automation begins

The core judgment call in this project — and the one I'd bring into any automation role — is that not every step belongs to the AI. Natural language understanding is the AI's job. Anything that has to be predictable, auditable and repeatable is a deterministic workflow's job, not a model's.

AreaTechnology choiceReason
Natural-language questionsAI / Copilot StudioUsers express the same need in many different ways
Knowledge groundingAI + controlled documentsUse approved sources, avoid inventing internal policy
Request captureAI extracts structured fieldsTurns conversation into system, justification, priority, approver, description
Approval & status logicDeterministic Power AutomateBusiness actions must be predictable, auditable, repeatable
Access decisionHuman in the loopSensitive permissions are never granted autonomously by AI

What's built

Power Platform foundation

Isolated M365 tenant, licensing, Power Platform environment, Dataverse, security roles.

SharePoint system of record

An IT Requests list tracks every request as a structured, auditable record.

Approval workflow

New request → Pending Approval → approval → Approved/Rejected → update → email, fully deterministic.

Grounded assistant

Copilot Studio agent grounded on three internal policy documents — no answers invented.

Safety behaviour

Least privilege by default, no credential handling, escalates unknowns, never grants access itself.

Request-creation tool

Agent tool extracts six structured fields from free-text conversation.

Known limitation — and why I'm showing it

The agent correctly identifies the request-creation intent and populates all six workflow inputs. The tool call itself returns HTTP 403, with zero workflow runs in monitoring — meaning the request is blocked at the agent-to-workflow authorization boundary, before SharePoint or workflow logic ever executes.

Planned fix: validate runtime entitlement and licensing in a fully licensed tenant, check environment ownership and runtime permissions, test the classic Agent Flow bridge, and use a dedicated least-privilege service identity. A PoC that only shows the happy path isn't proof of much — diagnosing why something breaks, not just that it does, is most of the actual job.

Security & governance

  • Least privilege — broad administrator access is challenged by default
  • Human approval — the AI never grants access autonomously
  • Prompt safety — passwords, MFA codes, API keys, tokens and private keys are never requested or stored
  • Data minimization — only information required for the process is collected
  • Grounding & escalation — unsupported questions are escalated, never answered from general knowledge
  • Production separation — real deployment needs controlled Dev/Test/Prod, DLP policies, monitoring, formal ownership

Path to production

Resolve the authorization issue → move demo knowledge files to permission-aware SharePoint sources → add employee self-service status lookups → add resilience (retries, logging, monitoring) → pilot with a small group → measure self-service rate, approval time, and escalation rate → productionize with a real permission model, DLP, and GDPR review.

Proof of concept built in an isolated Microsoft 365 tenant with fictional policies and test data — not a production deployment, not affiliated with any employer. Full project documentation (PDF) and setup notes are in the GitHub repo.
